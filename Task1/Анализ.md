# Анализ работы с данными

## Исходное состояние

«Медикаменте» ведёт записи, карточки, результаты анализов и часть платежей в Excel и сканах на общем диске. Учет платежей и кадров ведётся в файловой 1С:Бухгалтерии, ТМЦ — в 1С:Торговле и складе. Сервер расположен в офисе. Из защиты в описании подтверждена доменная аутентификация; прикладного разграничения и аудита нет. О наличии шифрования, резервного копирования и антивируса сведений нет.

В задаче указаны 20 административных сотрудников, но перечислены только 15. Дополнительные должности и права не назначаются без уточнения. Канал поступления результатов лаборатории не описан; действующий API не предполагается.

## Проблемные зоны

| № | Факт или пробел | Риск для процесса | Предлагаемая мера |
|---|---|---|---|
| 1 | Пациенты, договоры, медкарты и анализы лежат в файлах; каталог чувствительных полей отсутствует в описании | Неучтённые копии и лишние поля | Инвентаризация файлов и полей, владельцы, классификация, регистрация копий |
| 2 | Только доменная аутентификация, нет ограничений систем обработки | Вошедший сотрудник получает избыточный доступ | Группы AD и ACL немедленно; прикладные RBAC/ABAC в целевой системе |
| 3 | Внутренние потоки не контролируются | Передача медицинских данных получателям без необходимости | Минимальные контракты, разрешённые направления, TLS, проверка цели |
| 4 | Нет аудита чтения и изменения | Нельзя восстановить историю доступа и заметить массовую выгрузку | Защищённый журнал доступа, изменений и экспорта; алерты |
| 5 | Платежи дублируются в Excel и 1С | Расхождение статуса оплаты и двойной учёт | 1С — владелец бухгалтерских записей; сверка по идентификатору платежа |
| 6 | Все продукты на одном физическом сервере | Общая точка отказа при росте и миграции | Разделение нагрузок, защищённая резервная копия, проверяемое восстановление |
| 7 | Исходные данные ручные и разного формата | Дубли пациентов, неверная привязка анализов | Справочник patient_id, валидация импорта и ручная проверка спорных соответствий |
| 8 | Сроки, основания обработки и удаления не описаны | Избыточное накопление или ошибочное удаление обязательных документов | Реестр целей и оснований, отдельная политика сроков, контролируемые запросы субъектов |
| 9 | Планируются лабораторный API и личный кабинет | Получение пациентом чужих данных по подменённому ID | Авторизация каждой операции по владельцу записи; ограничения партнёра и контракта |
| 10 | Планируются BI/ML/AI и озеро | Перенос полной медкарты в аналитику и повторная идентификация | Закрытый raw, псевдонимизация, разрешённые признаки, агрегаты и оценка риска |
| 11 | Меры защиты носителей, бэкапов и ключей не описаны | Утечка при копировании диска или резервной копии | Инвентаризация защиты; шифрование и отдельный KMS, проверка восстановления ключей |

Описанные риски — анализ учебного кейса. Пробел в описании не доказывает отсутствие конкретного защитного продукта или уже произошедшую утечку.

## Данные и способы защиты

| Категория | Примеры | Основная защита | Минимизация и представление |
|---|---|---|---|
| PII | ФИО, дата рождения, телефон, email, адрес, работа/учёба | Шифрование носителя и выбранных полей; TLS; RBAC/ABAC | Для записи — идентификатор, контакт, специалист и время; остальные поля только по цели |
| PHI | Диагноз, хронические заболевания, медкарта, анализы | Шифрование, доступ по лечебному отношению, аудит | Не передавать ресепшену, складу и обычной бухгалтерской отчётности |
| Финансовые | Сумма, платёж, договор, зарплата и налоговые сведения | Закрытые финансовый/кадровый домены, шифрование и сверки | В запись на приём отдавать только статус оплаты, если он нужен процессу |
| Внутренние | ТМЦ, поставки, оборудование | Ролевой доступ и целостность | Не добавлять сведения о пациенте в складские документы |
| Метаданные | Идентификаторы, теги, lineage и аудит | Разграничение, защита от изменения, ограничение срока | Не записывать диагноз, ФИО, телефон и тела API в технические журналы |
| Аналитические | Подготовленные признаки и агрегаты | Псевдонимизация до выдачи, отдельные права и ключи | Удаление прямых идентификаторов, обобщение дат, подавление малых групп |

Обфускация и маскирование используются для отображения ограниченных полей и безопасных тестовых копий. Оригиналы медкарт ими не заменяются. Псевдонимизированный набор остаётся чувствительным, пока сохраняется возможность связать его с человеком.

## Тегирование и применение правил

1. Владелец процесса утверждает словарь: `category`, `domain`, `owner`, `purpose`, `retention_policy`, `source`, `layer`, `policy_version`. Для файла дополнительно хранится ID объекта и контрольная сумма; для БД — таблица и поле. Один объект может иметь несколько категорий, например PII и PHI.
2. Реестр метаданных в PostgreSQL хранит словарь, классификацию полей, зарегистрированные файлы и связи преобразований. Это минимальный каталог MVP. Сканер, например Microsoft Presidio с правилами для русскоязычных реквизитов, предлагает метки; ответственный проверяет их. Для JPG/PDF требуется OCR и ручная проверка. Отсутствие найденной PII не считается доказательством безопасности.
3. Импорт работает через карантин. Неклассифицированный файл не попадает в общие витрины. API и ETL проверяют обязательные теги и разрешённую цель. Изменение классификации журналируется; понижение чувствительности требует владельца данных.
4. При копировании и преобразовании сохраняются ссылка на источник, ID запуска и версия правила. Производные поля наследуют чувствительность исходных данных; понижение возможно только после проверки преобразования и риска повторной идентификации. Каталог не получает полные значения медкарт.
5. Политика доступа применяется сервером: роль, категория, цель, филиал и связь врача с пациентом. Для пациента проверяется соответствие ID записи его учётной записи. IAM сам по себе не читает теги всех таблиц. PostgreSQL RLS используется как дополнительный рубеж для прикладных ролей; владелец БД не должен быть рабочей ролью API.
6. Проверки релиза сравнивают схему и каталог, требуют классификацию новых полей, проверяют ответы API и запрет чужих записей. ETL блокирует выгрузку PHI/PII в неподходящий слой. Аудит и мониторинг обнаруживают чтение большого количества записей и несогласованные экспорты.

MVP использует реестр и явные проверки, без внедрения большого Hadoop-кластера. При росте можно заменить каталог специализированной платформой; наличие нужных коннекторов и их эксплуатационную стоимость сначала проверяют. Тегирование не заменяет политики и их исполнение.

## Диаграммы потоков

Файл «Потоки данных.drawio» содержит отдельные страницы As-Is и с мерами защиты для шести процессов: регистрация и запись; медицинская помощь; результаты анализов; оплата; бухгалтерский и кадровый учёт; складской учёт. Прямоугольники — участники, округлённые блоки — процессы, цилиндры — хранилища, стрелки — данные. На страницах с мерами подписаны меры в передаче и обработке, а в хранилищах — защита данных at rest.

Будущая аналитика показана отдельно в целевой архитектуре Task2. Она не выдаётся за существующий поток компании.
