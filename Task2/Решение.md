# Архитектура MVP и развитие

В «Контекст C4.drawio» две страницы. «C4 — контекст MVP» показывает людей, систему записи и соседние системы. «Защитные блоки и аналитические зоны» раскрывает все механизмы из таблицы ниже и путь данных до аналитической витрины. Это функциональная детализация: блоки не означают отдельные микросервисы или серверы.

## MVP через два месяца

Пациент записывается через клиентский портал. Ресепшен видит расписание, контакт и статус записи, но не диагноз. Врач видит свои приёмы и необходимые сведения о связанных пациентах. Сервис уведомлений создаёт напоминания пациенту и специалисту за сутки, не включая медицинское содержание. Оператор может обработать исключение вручную. Базовые данные контактов и расписания хранятся в разных схемах PostgreSQL с отдельными прикладными ролями. Физически отдельные серверы на каждый домен для MVP не обязательны.

Основные правила:

- Запись на слот выполняется транзакционно с ограничением уникальности активного слота. Повтор одного запроса не создаёт вторую запись.
- Доступ определяется на сервере. Пациенту доступны только собственные объекты; роль пациента недостаточна без проверки владельца. Врач получает доступ по назначению или лечебному отношению, ресепшен — по рабочему филиалу.
- Сотрудники входят через существующий AD и посредник IAM; пациентские учётные записи отделены от доменных. Предлагается Keycloak с проверкой нужной интеграции с AD; MFA — для привилегированных ролей. Каталог тегов и прикладная авторизация работают отдельно от IAM.
- Реестр метаданных, аудит, шифрование, управление ключами и минимальные API-контракты включаются сразу. Доступ по умолчанию запрещён. API не принимает от клиента роль или владельца как доверенное основание доступа.
- Общие файловые архивы и 1С пока сохраняются за адаптерами. Новое расписание — единственный владелец новых записей после переключения. Полные медицинские документы не копируются в базу расписания.

## Защитные блоки

Таблица поясняет механизмы второй страницы. Их названия совпадают с подписями схемы. На первой странице внутренние функции сведены в общий блок системы записи.

| Механизм | Назначение | Где реализуется и как связан на схеме |
|---|---|---|
| AD + IAM | Личность, роли и сессии; раздельные пациентские и служебные учётные записи | Отдельный блок на обеих страницах. Передаёт в «Порталы / API» проверенные сведения о личности и ролях; доступ к конкретному объекту проверяет API. |
| Серверная политика доступа | Проверка категории, владельца записи, филиала и лечебной связи; минимальные ответы | Указана внутри блока «Порталы / API». Получает правила из «Каталог и политики», проверяет операции с PostgreSQL и обращения через адаптеры. |
| Каталог и политики | Теги, цели, владельцы, сроки, источники и версии преобразований | Отдельный блок второй страницы. Получает метаданные доменов; выдаёт правила API и подготовке аналитических данных. Полные медицинские значения в каталог не копируются. |
| KMS и защищённые носители | Отдельное хранение ключей, ротация, восстановление и ограничение сервисных прав | Отдельный блок второй страницы; связь с PostgreSQL показывает обслуживание ключей. Шифрование также требуется для аналитических зон и копий; остальные связи с KMS опущены для читаемости и перечислены в примечании схемы. |
| Аудит и мониторинг | Кто, когда, к какому объекту и с какой целью обратился; алерты без полного медицинского содержания | Отдельный блок второй страницы. Принимает события API. События ETL и выдачи витрин также поступают в аудит; эти связи перечислены в примечании схемы. |
| Адаптеры legacy | Стабильные контракты к 1С и файловому архиву; ограниченные сервисные права | Компоненты приложения: «Порталы / API» → «Адаптеры legacy» → «1С и файловый архив». На первой странице это одна укрупнённая связь между системами. |

Стрелки второй страницы показывают взаимодействия, а не полный сетевой протокол: ответ может возвращаться по той же связи. В аналитической части стрелки показывают направление подготовки и выдачи данных. IAM подтверждает личность, каталог хранит правила, API и ETL применяют их; наличие IAM или каталога само по себе не ограничивает доступ к записи.

## Аналитический слой

Предлагается три зоны в инфраструктуре РФ. Закрытый raw принимает разрешённые выгрузки Excel/сканов через карантин, а не открывает аналитикам общий диск. Подготовка валидирует формат, устраняет дубли, регистрирует lineage и заменяет patient_id аналитическим токеном. Таблица соответствий находится в отдельном защищённом хранилище. Для BI публикуются минимальные агрегаты; малые группы подавляются или укрупняются по утверждённому правилу. Порог и риск повторной идентификации проверяют до публикации.

На MVP достаточно ограниченного импорта и согласованной агрегированной витрины. Озеро и выделенный ClickHouse развиваются по нагрузке; BI не читает OLTP напрямую. Для ML/LLM выдаётся отдельный одобренный набор признаков после проверки цели, состава, оснований и риска раскрытия. Медкарты не загружаются в сторонние AI-сервисы. Теги и lineage продолжаются через raw, подготовленный слой и витрину; маска прямых идентификаторов не делает набор автоматически анонимным.

## Финальное состояние через год

Добавляются мобильное приложение, подтверждение/отмена, CRM, медицинский домен и интеграция лаборатории. API лаборатории получает идентификатор заказа и минимальный набор, необходимый для анализа; результаты привязываются к заказу и доступны только разрешённым участникам. Платёжный шлюз передаёт в систему статус и внешний ID платежа. Карточные реквизиты остаются у платёжного провайдера. Новые интеграции используют общий шаблон политик, но каждый новый контракт всё равно проверяется.

## Жизненный цикл и эксплуатация

Запрос на прекращение обработки проходит проверку личности и применимых оснований. Необязательная обработка прекращается; обязательное хранение выделяется в закрытый архив с ограниченным использованием. Конкретные сроки утверждаются по типам медицинских, кадровых и финансовых документов. Удаление охватывает производные наборы и копии; восстановление из бэкапа повторно применяет журнал удалений и ограничений.

Резервные копии шифруются и хранятся отдельно от рабочего сервера и ключей. Цели RTO/RPO согласуются до запуска. Нагрузочная проверка охватывает рост данных в пять раз, параллельные записи, импорт и формирование отчёта. Время отклика и доступность ещё не измерены; они не объявляются достигнутыми.

Для трёх IT-специалистов предлагается модульное приложение и несколько инфраструктурных сервисов, а не множество микросервисов и обязательный Kubernetes. При найме можно выделять сервисы по измеренным ограничениям. Конфигурации ролей, политик и каналов уведомлений версионируются и проверяются до применения.
